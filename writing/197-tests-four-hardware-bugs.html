197 passing tests, four real-hardware bugs

The unit suite was green. Then I gave the program an RDMA device.

Claim. The first real-device CI run of roce-preflight exposed four defects that 197 passing unit tests had not. The useful lesson is narrower than “hardware testing is good”: tests built from fixtures generated by the same implementation can establish internal consistency while leaving the system boundary almost completely untested.

The credibility gap

roce-preflight diagnoses whether a RoCE host is actually ready to bring queue pairs up. It reads GID tables, port state, MTU and host configuration; it can also drive RC, UC and UD queue pairs through the verbs lifecycle. Early on, the repository had 197 passing unit tests. That sounded reassuring until I asked what those tests actually touched.

They exercised parsers, ranking logic, synthetic snapshots and lifecycle decisions. They did not require an RDMA device. The fixtures were representations of the world that the repository itself had written. A green suite therefore established a useful but much narrower property: the implementation agreed with its own model.

A test suite cannot validate a boundary it never crosses.

The experiment

I added a CI job whose purpose was not more coverage but a different evidence class. GitHub's Ubuntu runner does not ship rdma_rxe for its Azure kernel, so the job builds the upstream soft-RoCE kernel module against the running kernel, creates rxe0, and then asserts that backend detection has not fallen back to simulation. Only after that assertion does it run the inspectors, queue-pair lifecycle, and real ib_write_bw traffic.

The distinction matters. Soft-RoCE is not a performance proxy for a physical NIC, but it is a real Linux RDMA device with real verbs, real sysfs state and a real GID table. That makes it sufficient to test whether the software's assumptions about those interfaces survive contact with the kernel.

Reproduction path
The workflow is public at .github/workflows/soft-roce.yml ↗. It builds rdma_rxe.ko, creates rxe0, asserts backend != simulate, dumps the real GID table, runs doctor/hostpath/QP checks, sends perftest traffic and finally reruns the unit suite on a host that actually has RDMA.

None of these failures required exotic hardware. They required the program to stop talking to an imitation of Linux RDMA and talk to Linux RDMA.

The most valuable failure was the attempted fix

The first correction attempt is the part I care about most. It passed the unit suite and changed nothing on the real device. Hardware CI rejected it immediately. That converted the real-device job from a one-time debugging aid into a permanent acceptance boundary: a fix to an RDMA path is not accepted merely because the model says it should work.

After correction and hardware re-verification, doctor reported the active MTU consistently, the diagnosis agreed with the live GID state, the snapshot contained three GID entries, and RC/UC/UD all reached payload verification. The suite had grown to 208 tests, but the meaningful addition was not eleven more tests. It was one test environment with independent state.

197 → 208 is not the story. Synthetic state → independent device state is the story.

Why simulation failed here

Simulation was doing exactly what it was designed to do. It made edge cases deterministic and allowed the logic to run without privileged hardware. The mistake would have been assigning it authority it did not have.

There are at least three distinct things to validate in this kind of systems tool: logic—does the algorithm behave correctly for a supplied state; interface fidelity—does the supplied state actually look like the kernel/device interface; and physical behavior—does traffic behave correctly on the target hardware and fabric. Unit fixtures were strong on the first. Soft-RoCE CI materially improved the second and exercised real verbs for part of the third. It still cannot validate physical-NIC firmware, PCIe behavior, switch configuration, PFC/ECN behavior or multi-host routing.

The strongest counterargument

These four defects could be described as ordinary mocking mistakes. That is true. Better fixtures could have reproduced each one after it was known. But that is also the reason the hardware boundary matters: before the failures were known, the implementation and its fixtures shared enough assumptions that both could be wrong in the same direction.

A mock becomes dangerous when it is treated as independent evidence. Its highest-value use is fast deterministic testing of already-understood behavior. Its weakest use is discovering that your mental model of an external system is wrong.

What I changed in the test architecture

The project now treats evidence as tiers rather than collapsing everything into “tested.” Unit tests protect deterministic logic. The real-device job must prove it did not silently fall back to simulation. Inspectors must read real sysfs state. Queue-pair tests expose the underlying verbs error rather than swallowing it into a summary. Real traffic is sent through ib_write_bw. Synthetic performance numbers are labeled synthetic rather than being presented as qualification data.

The same rule appears in the product itself: observed, analysis-only and synthetic capabilities are separated. That is partly a UX choice, but mostly an epistemic one. A diagnostic tool should be unusually explicit about which parts of its own diagnosis have touched reality.

What this result does not prove

Boundary of the evidence
This was soft-RoCE on a single GitHub-hosted Linux machine. It proves that the code traversed real RDMA kernel/userspace interfaces and real verbs. It does not prove performance or correctness on mlx5 hardware, a two-node RoCEv2 fabric, production switches, SR-IOV/VF topologies, vendor firmware, PFC/ECN configuration, PCIe/NUMA placement or failure under sustained load. Those require different experiments. The project explicitly keeps those claims separate.

What would change my mind?

If an independently maintained simulator or generated fixture system repeatedly caught the same interface-assumption defects before real-device execution, I would weaken the claim that a device boundary is uniquely valuable here. If future hardware runs stop finding defect classes that are absent from unit/simulation coverage, the marginal value of the job may become regression protection rather than discovery. Either outcome would be useful.

The engineering rule I kept

The lesson is not to replace unit tests with integration tests or simulation with hardware. The fast layers are what make iteration possible. The rule is to know what proposition each layer can actually support.

For roce-preflight, 197 green tests supported “the implementation is internally consistent across these modeled cases.” They did not support “this works on RDMA.” One two-minute job changed the evidence behind that sentence.

When the external system is part of the claim, make the external system part of the test.
