Autograd is part of the API

An activation can return the expected forward value and still be wrong if its learnable parameter cannot move through the function it supposedly controls.

UpstreamMatGL #809 merged
Regression suite92 layer tests
Forward diff0–5e-7 in valid region
FailureNaN/Inf gradients

Claim. For differentiable ML software, the public behavior of a function includes the gradient path, not only its forward values. A Python branch over a learned tensor can preserve plausible outputs while violating the optimization semantics the API implies.

The code looked ordinary

MatGL's SoftExponential activation has a learned parameter α and three mathematical regimes: negative α, zero, and positive α. The implementation selected them with Python if statements over the parameter.

That is a subtle boundary violation. Evaluating if self.alpha < 0 asks Python for a boolean value from a tensor. The branch decision occurs outside the differentiable tensor program. The forward pass can still look correct for the current sign of α, but the learned parameter is no longer participating in the function in the way the optimizer expects.

The zero branch had a second problem: exact equality to 0.0 is not a useful numerical neighborhood for a parameter being updated by gradient descent. Once α moves to a tiny nonzero value, the intended identity-limit behavior is skipped.

The third bug was more visible

For negative α, the logarithm's argument becomes non-positive for sufficiently negative inputs. That produced NaN/Inf outputs and propagated invalid values into alpha.grad. A single activation could therefore poison training without an obvious structural error in the model.

Forward correctness, numerical-domain correctness, and gradient correctness are three separate contracts.

The fix had to satisfy all three

The merged patch moved branch selection into tensor operations with torch.where, used an epsilon neighborhood for the α→0 identity regime, guarded undefined logarithm and denominator regions, and used expm1 in the positive branch for better near-zero numerical behavior.

There is a nasty detail here: torch.where selects outputs, but both branches may still be evaluated. That means the branch you intend to discard must also remain numerically safe. The patch therefore had to guard the unused formula as well as the selected one.

In the well-defined region, the new implementation matched the old forward formula to a reported maximum absolute difference of 0–5×10⁻⁷. The change was not a new activation; it was making the existing activation obey the differentiable interface it already advertised.

The regression tests changed the definition of “works”

The added tests do not merely compare outputs. They ask whether the activation remains finite for large-negative inputs, whether alpha.grad remains finite, and whether α receives a finite nonzero gradient from both sign initializations. The full layer suite passed 92 tests after the change.

One existing test also had to switch from .numpy() to .detach().numpy(). That tiny change is almost a proof of the bug: after the fix, the output correctly belonged to an autograd graph where the old code had short-circuited around it.

The strongest counterargument

A hard branch on the sign of a parameter is mathematically natural because the SoftExponential definition itself is piecewise. The issue is not piecewise mathematics. It is implementing that mathematics in a way that changes the semantics of a learned tensor when control crosses from the tensor runtime into Python.

There are contexts where a non-differentiable branch is intentional. A trainable activation with α presented as a learned parameter is not one of them.

The more general rule

When reviewing ML infrastructure, I now treat gradients like serialization or thread safety: they are part of the interface even if they are not visible in the function signature. A test that only asserts y == expected can miss a model component that optimization cannot actually use.

If a parameter is learnable, “does the value look right?” is only half the test.

What this does not establish

Boundary. This patch fixes a specific activation implementation. It does not imply that every Python conditional over tensors is a bug, nor that torch.where is always the correct replacement. The relevant question is whether the control decision is supposed to remain part of the differentiable program and whether all evaluated numerical branches are safe.
