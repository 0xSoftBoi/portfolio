Date and time bugs are systems bugs

Four small compatibility patches taught me the same lesson: time software fails at the boundary between a mathematically valid representation and the behavior users have already built systems around.

Claim. Date/time correctness is compatibility engineering. A parser can accept a timestamp and still be wrong if it chooses the wrong rounding convention, preserves the wrong timezone for display, or recognizes a grammar differently from the reference implementation.

The timezone was correct and the output was wrong

In uutils date, one parsing path treated a trailing timezone abbreviation as both the timezone of the input and the timezone of the output. Under TZ=UTC, parsing 2024-01-01 EST produced midnight at -05 instead of 05:00 UTC.

Both timestamps can describe the same instant. Only one matches GNU date's observable contract: the abbreviation describes the input, then the result is re-zoned into the local output timezone. The fix was not “timezone math”; it was restoring a boundary between interpretation and presentation.

Negative time exposes rounding policy

Another bug came from a timestamp helper that truncated toward zero. For @-1.5, truncation gives -1; GNU-compatible epoch-second behavior requires floor semantics, giving -2.

That difference is one second, but it is not noise. It is a choice about how fractional instants before the Unix epoch map into integer seconds. PR #285 added an explicit unix_epoch_second() with floor behavior and normalized fractional nanoseconds, with seven regression tests including @-1.5 → -2.

A time representation is not only a number. It carries conventions for timezone, rounding, grammar, and display.

Grammar can fail because a parser succeeds too early

The combined date-time parser also failed on inputs such as 2024-06-15 12:00 PM. The 24-hour ISO parser greedily accepted 12:00 and left PM orphaned. The fix was to use the broader time parser that tries the AM/PM grammar before falling back to ISO.

This is a classic parser-composition problem: a sub-parser can successfully consume a prefix and still make the whole parse wrong. Correctness lives at the grammar boundary, not the local return value.

Sometimes compatibility is one missing string

GNU date -d accepts bare UT as Universal Time. The parser already accepted UTC and GMT but omitted ut from its normalized abbreviation table. The implementation change was essentially one mapping; the engineering value was preserving an established user-facing language.

That patch is a good antidote to the idea that line count tracks importance. Compatibility software accumulates meaning through thousands of tiny behavioral promises.

Why I group these patches together

None of these bugs is algorithmically dramatic. Together they reveal a systems pattern:

Representation. A timestamp library chooses a numeric model.
Interpretation. A parser maps human syntax into that model.
Policy. The tool chooses rounding, timezone, and normalization conventions.
Compatibility. Existing software and users depend on those choices being the same tomorrow.

A change can be internally consistent across the first three layers and still be wrong at the fourth.

The strongest counterargument

Cloning GNU quirks can fossilize historical behavior instead of designing a cleaner interface. That is true for new software. Coreutils compatibility has a different product contract: scripts depend on the reference behavior, including edge cases that would not be chosen from first principles.

The right engineering question is therefore not “what would be the prettiest date API?” It is “which semantics has this implementation promised to reproduce?”

In compatibility software, an edge case is often someone else's production interface.

What this does not establish

Boundary. These four merged patches cover specific GNU-compatibility gaps: timezone re-zoning, negative fractional epoch seconds, combined AM/PM parsing, and UT aliases. They are examples of a broader class, not a claim of complete date/time compatibility.
