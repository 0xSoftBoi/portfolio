Engineering thesis · August 2026

Correctness under hidden failure modes

The systems I find most interesting are the ones that pass the obvious test and fail the important one.

A unit test can prove that a model of a NIC behaves correctly. It cannot prove that the NIC does. A benchmark can produce a precise score while accidentally measuring memorization. An uncertainty estimator can return a number for every prediction without that number containing useful information about error. A distributed protocol can satisfy its happy-path specification while failing under an adversarial transition nobody modeled.

I used to think these were different classes of engineering problem. Increasingly, I think they are the same problem: an abstraction has quietly become the object being tested.

The job is not to make the abstraction pass. The job is to find the cheapest experiment capable of proving the abstraction wrong.

Hardware is an adversarial reviewer

While building RDMA/RoCE diagnostic tooling, a large unit-test suite gave me confidence in the software. Real RDMA hardware then exposed defects the tests had missed. The lesson was not that unit tests are weak. It was that they answer a narrower question than I had allowed myself to believe.

That changed the design rule: every reported fact should say whether it was observed, inferred, or simulated. If a check requires hardware, an analysis-only substitute must not masquerade as the same evidence.

A benchmark can be wrong even when the code is right

In an AI-security evaluation, I found that benchmark prompts leaked information that made the headline result less trustworthy. The tempting response would have been to treat contamination as a footnote. Instead, it became the main result: strip the leakage, anonymize identity cues, rerun the same experiment, and report the paired delta.

Evaluation work is dangerous because numbers acquire authority faster than experimental designs do. A benchmark should therefore be treated like production infrastructure: threat-model it, test its invariants, and assume that convenient information will eventually find a path into the metric.

Uncertainty is not useful because it has units

In materials discovery experiments, MC-dropout produced an uncertainty value that looked like exactly the signal an acquisition strategy needed. Calibration told a different story. The uncertainty estimate was badly miscalibrated and, in the experiment, anti-correlated with absolute error. UCB barely improved over greedy ranking because the useful signal was the mean prediction, not the uncertainty term.

That negative result was more valuable than a small benchmark win. It converted a plausible mechanism into a falsified one.

Delete ambition until a claim becomes testable

Aiur started as a deliberately excessive idea: persistent lighter-than-air infrastructure acting as a carrier for autonomous drones. The useful engineering move was to delete almost all of it. No giant vehicle. No airborne data center. No charging. No swarm.

The first question is smaller: can a buoyant platform repeatedly recover a moving micro-UAV onto a mechanically positive dock? That question can fail. It can produce telemetry. It can be repeated. It can tell us whether the architecture deserves another dollar of complexity.

The common rule

Across networks, ML evaluation, scientific computing, cryptographic systems, and autonomous hardware, I now use roughly the same hierarchy of evidence: a claim is strongest when an independent person can reproduce the failure or measurement; weaker when it follows from a model; weaker still when it follows only from architecture or intent.

This makes engineering less comfortable. It also makes it faster. A good negative result kills an entire branch of work. A real-hardware failure can invalidate weeks of simulated confidence. A contaminated benchmark can save you from optimizing against a fiction.

I want tests that can embarrass the implementation, benchmarks that can embarrass the hypothesis, and hardware that can embarrass both.

That is the thread connecting the projects I want to keep working on: systems where correctness is not obvious, where the abstraction is useful but untrustworthy, and where measurement can still change your mind.
