A benchmark can measure its own metadata

I built an agentic security benchmark, published a score, then discovered that more than half of the prompts contained a description of the answer.

StatusBounded postmortem
Corpus24 verified contracts
Leakage13 / 24 severe
ConstraintNo paid remeasurement

Claim. BRIDGE-bench's original capability number cannot be interpreted as clean vulnerability-detection performance because 13 of 24 model prompts contained author-added provenance comments describing the exploit mechanism, and one particularly sharp case contained the exact ground-truth label for a bug whose vulnerable function was not present in the committed source.

The failure was upstream of the model

The benchmark began with a reasonable question: can a tool-using model find vulnerabilities in real deployed contracts? The dataset used verified contract source and provenance headers so a human could audit where each example came from. The mistake was that the loader sent the entire file to the model. Human-facing provenance had silently become model input.

A zero-cost audit of the exact prompt strings found 13/24 severe leaks: the header named an exploit and described its mechanism, or stated a ground-truth label. Seven more contained moderate incident metadata. After comments were stripped, severe and moderate leakage fell to zero; after protocol identity was neutralized, all 24 examples passed the audit's CLEAN condition.

The benchmark was not only evaluating the artifact. It was also evaluating the annotation attached to the artifact.

Euler made the problem undeniable

The Euler example's header described donateToReserves, explained the missing solvency check, and literally included missing_solvency_check. Opus returned that label and the scorer counted a true positive.

But the vulnerable donateToReserves function was not in the committed source bundle. After comment stripping, the symbol disappeared entirely. In that example, the code could not have supported the claimed detection because the relevant vulnerable function was absent. The answer existed in the comment.

That does not prove every model finding was metadata recognition. It proves the published aggregate mixed at least two mechanisms—code analysis and prompt leakage—in a way the headline score could not separate.

The number I stopped claiming

The original Opus 4.8 run reported 35% semantic F1 and 54% recall across 24 contracts. Those measurements are real, but their interpretation changed. They are now labeled contaminated upper bounds rather than detection performance.

The experiment that would identify the size of the effect is paired remeasurement at three prompt levels: raw, comments stripped, and identity anonymized. I built and validated that pipeline, but I am not running the paid model calls. Therefore this note makes no claim about the magnitude of Δ(raw→stripped) or Δ(stripped→anon). The absence of that result is part of the result.

The fix is a measurement design, not a regex

The sanitizer has three levels: raw reproduces the original prompt; stripped removes author-added comments; anon additionally neutralizes protocol identity. The useful part is not merely deleting comments. It is making each transformation auditable.

The verifier checks that comment stripping preserves the code-token stream, identity replacement is whole-word and collision-checked, and structural fingerprints remain identical. That safety layer caught a real bug while the sanitizer was being built: an address-neutralizing expression started rewriting the first 40 hexadecimal characters of 64-character bytes32 constants. Without the invariant, a lower post-sanitization score could have been caused by the sanitizer corrupting the program.

Zero-cost reproduction
Leakage audit ↗ · python -m benchmarks.sanitize. The audit distinguishes author-injected provenance from comments that belong to the original verified source. It intentionally does not count ordinary NatSpec or source comments as leakage merely because they are informative.

The strongest counterargument

A model that sees a prose description of a bug may still need to locate and explain the vulnerable code, so leakage does not automatically reduce a finding to trivial copying. That is correct for many examples. It is why I do not subtract 54% from the score or claim the model had zero detection ability.

The Euler case establishes that at least one scored detection could not have come from the committed vulnerable code. The corpus-level audit establishes that the confound was systematic. The missing paid paired run means the causal size remains unknown.

The general lesson

This failure pattern is not specific to Solidity. A benchmark assembled from public incidents can accidentally expose the target through filenames, issue titles, CVE descriptions, postmortem summaries, comments, commit messages, or provenance fields. The model may then appear to recover a capability when it is recovering the dataset's curation history.

The simplest pre-publication test is embarrassingly cheap:

Print the exact string the model receives. Grep it for the label. Then grep it for a prose description of the answer.

I did that after publishing a number. I now do it before trusting one.

What this does not establish

Boundary. This note establishes prompt contamination in the original corpus and validates a zero-cost sanitization path. It does not establish sanitized model performance, memorization rate, or the causal effect size of the leakage. Those require model remeasurement that is intentionally outside the current zero-cost writing program.

What would change my mind?

A paired raw/stripped run showing no meaningful degradation would weaken the claim that the leakage materially inflated aggregate performance, while leaving the dataset-design flaw itself intact. A de-identified matched-pair benchmark with strong performance would provide much better evidence of genuine code-analysis capability than another famous-exploit score.
