A default is executable policy

Three changed defaults in MLX-LM fixed a configuration that could turn “enable XTC” into “throw away nearly the whole candidate distribution.”

UpstreamMLX-LM #1372 merged
Filessampler · CLI · server
Old threshold0.0
New threshold0.1

Claim. Configuration defaults are part of an inference system's semantics. A feature can be implemented correctly and still behave pathologically when its defaults compose into a state no user intended.

The bug was not in the sampler formula

MLX-LM's XTC sampler takes a probability threshold and a probability of applying the transformation. The old default threshold was 0.0. If a user set xtc_probability > 0 but left the threshold alone, the masking rule considered every token with probability above zero eligible.

For an ordinary softmax distribution, that means almost every token. The resulting mask preserves the least-probable edge case instead of applying a nuanced truncation rule. The feature is technically “on,” but the default composition inverts the spirit of the control.

The dangerous state was not an invalid parameter. It was the documented path of setting one parameter and trusting the other.

Why this kind of bug survives review

Each component looked locally reasonable. A threshold accepts zero. A probability defaults to disabled. The masking function does what its inputs say. The failure appears only when a user changes one knob and relies on the default of another.

That is a common inference-systems failure mode: implementation review focuses on kernels and algorithms while the operational behavior emerges from a layer above—CLI defaults, API body defaults, config merging, and aliasing.

The fix was deliberately boring

The merged patch changed the XTC threshold default from 0.0 to 0.1 in all three public entry points: make_sampler(), the generation CLI, and the server request body. Three additions, three deletions.

That “everywhere” matters more than the line count. A server and CLI that disagree on a sampling default are effectively two inference products sharing code. Correctness includes keeping the public surfaces semantically aligned.

The strongest counterargument

Users enabling an advanced sampler should set all relevant parameters explicitly. That is defensible for low-level libraries, but MLX-LM exposes these controls through end-user CLI and OpenAI-style server interfaces. Once a parameter has a default, the software is making a policy decision on behalf of users who omit it.

A default should therefore be judged by the behavior it creates under the most natural partial configuration, not only by whether the value is inside the parameter's mathematical domain.

The general rule

For inference systems, I now treat defaults as a small program. The review question is not “is every default individually valid?” but “what execution path appears when a user changes exactly one obvious control?”

This is especially important for sampling, caching, quantization, context limits, speculative decoding, and adapters—places where a hidden configuration interaction can change model behavior without throwing an error.

If the system accepts a partial configuration, the defaults complete the program.

What this does not establish

Boundary. The patch establishes a pathological default interaction and aligns three MLX-LM surfaces to a safer threshold. It does not establish that 0.1 is optimal for every model or workload. Sampling policy remains task-dependent; the correctness claim is about avoiding the degenerate 0.0 composition.
