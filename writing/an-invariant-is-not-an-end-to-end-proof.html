An invariant is not an end-to-end proof

The most useful bridge invariant I wrote fits on one line. The important part was learning exactly what that line could—and could not—prove.

Claim. Security invariants are most valuable when their trust boundary is explicit. For a lock-and-mint bridge, wrapped.totalSupply() ≤ vault.totalLocked() captures the accounting property that must never fail, but enforcing it with attestations does not magically prove that a remote-chain event occurred. It makes an operator-coordination assumption enforceable on-chain.

The bridge reduces to one accounting sentence

A lock-and-mint system should never mint more wrapped assets on the destination than it has collateralized on the source. In the lab, that becomes a Foundry invariant:

wrapped supply ≤ locked collateral

That line is useful because it ignores product architecture and asks what failure means economically. If an adversary can forge the destination authorization and mint without a corresponding lock, the invariant breaks immediately.

The gate binds the decision, not the universe

Every value-moving action in the lab—mint, unlock, refund—passes through a verifier over a digest binding the domain, chain ID, contract address, commit ID, recipient, amount, and source-chain ID. Those fields close distinct replay surfaces: deployment, chain, operation type, and duplicate execution.

A commit can reach only one terminal source-side outcome, unlocked or refunded, which closes the “minted and refunded” double-spend path at the local state machine.

This is real enforcement, but the verifier still represents an authority decision. An ECDSA attestation says the configured operator set authorized this digest. It does not cause the EVM contract to independently observe another chain.

Cryptographic authorization can prove who approved a statement without proving the statement was true.

The mutation test matters more than another happy path

The invariant suite drives the system with both honest behavior and adversarial forged attestations across 512 runs with depth 100. It checks that supply never exceeds collateral and that the adversary mints nothing.

The more useful test deliberately disables the attestation gate. With the fix removed, the same forged mint succeeds and breaks the supply invariant in one call. That mutation test answers a question ordinary regression coverage often does not: is the security mechanism actually what prevents the failure?

A security test that still passes after the intended defense is removed may be testing the wrong thing.

Historical examples are controls, not reenactments

The repository includes minimal Ronin-, Wormhole-, and Nomad-shaped reproductions to show how the gate rejects categories such as unauthorized operators, unverified mint paths, and default/zero proof authorization.

They are deliberately not fork-level exploit recreations. That limitation is important. A small model can isolate a mechanism; it cannot inherit the evidentiary weight of a faithful historical reproduction merely because the names are familiar.

The strongest counterargument

If the operator quorum is itself trusted to attest remote events, then the supply invariant can hold while the bridge still accepts a false remote event signed by the quorum. Correct. The invariant protects a local accounting relation under the verifier's authorization model. It does not solve Byzantine operator truthfulness or provide a light-client proof.

That is why I prefer this lab to a diagram claiming “trustless bridge.” It exposes the exact property the contracts enforce and leaves the external assumption visible.

The design lesson

Distributed-system security often fails when a local proof is narrated as a global proof. A signature verifies authorization. A state-machine invariant verifies local transitions. A Merkle proof verifies inclusion relative to a root. None of those, alone, establishes the provenance of the root, the honesty of the signer set, or the liveness of the remote system.

Name the invariant. Then name the assumption it sits on top of.

What this does not establish

Boundary. The lab is unaudited and not production software. Its historical tests are minimal stand-ins. The supply≤collateral property is an operator-coordination property made enforceable on-chain; the contracts do not independently prove remote-chain events. The repository states these limitations explicitly.
